반갑꼬리

"반려동물 동반 가능"이라고 적혀 있어도 막상 가면 다릅니다. 10kg까지만, 소형견만, 실외 좌석만 — 조건은 제각각인데 어디에도 정리돼 있지 않습니다. 우리 아이의 몸무게와 품종을 기준으로 시설의 동반 조건을 근거와 함께 확인하는 앱을 만들었습니다.

Problem

데이터는 있는데, 답이 안 나온다

한국관광공사 반려동물 동반여행 데이터에는 4만 8천여 곳이 있습니다. 그런데 이 프로젝트의 DB 분류에서 조건을 파싱한 곳은 626건, 약 1.3%였습니다. "일부 구역 동반가능", "10kg 미만 소형견에 한함" 같은 문장을 규칙으로 바꾸되, 모호하거나 조건이 없는 데이터는 구분해야 했습니다.

그래서 이 앱의 핵심은 지도가 아니라 판별입니다. 자연어 조건을 파싱해 규칙으로 바꾸고, 등록된 반려동물의 몸무게·품종과 대조해 "가능 / 조건부 / 어려움"을 근거와 함께 보여줍니다.

DB 실측 기준 PARSED 626건(1.28%) · AMBIGUOUS 468건(0.96%) · NO_CONDITION 47,692건(97.76%). 조건이 없는 97%를 "가능"으로 단정하지 않는 것이 이 서비스의 설계 전제입니다. 분류 비율은 데이터의 상태를 나타내며, 판별 정확도나 실제 입장 가능 비율이 아닙니다.

Planning

지도보다 먼저 ‘조건을 믿을 수 있는가’를 정했습니다

백엔드 2명과 함께한 3인 프로젝트에서 핵심 기능을 자연어 조건 파싱으로 좁혔습니다. 검색·리뷰·게임 요소를 모두 동시에 키우기보다, “우리 강아지가 실제로 들어갈 수 있는가”에 답하는 데이터 흐름을 P0로 두고 탐색 화면과 부가 기능은 그 결과를 설명하는 범위에서 확장했습니다.

P0 · 판별
시설 원문 → 조건 파싱 → 반려동물 몸무게·품종 대조 → 가능 / 조건부 / 어려움과 근거 표시
P1 · 탐색
지역·지도·코스·리뷰를 붙이되, 파싱되지 않은 조건은 “확인 필요”로 남겨 과장하지 않기
결정 방식
시설상세 카드에 파싱 키워드를 전부 노출할지 팀원과 의견이 갈렸을 때, 두 버전을 직접 구현해 비교한 뒤 상세페이지로 옮기는 팀원 판단을 채택

말로 설득하는 대신 두 안을 실제 화면으로 만들어 정보 밀도와 사용 흐름을 비교했습니다. 팀원의 판단이 더 나았다는 걸 인정하고 기획을 수정한 협업 사례입니다.

AI Agent Development

자연어를 규칙으로 바꾸는 과정을 쪼개서 지시했습니다

Claude Code와 Codex에는 파싱 로직과 화면 연동을 한 번에 만들라고 하지 않고, 원문 정규화 → 키워드 추출 → 구조화된 조건 저장 → 반려동물 프로필과 판정 → 설명 문구 생성 순서로 나눠 지시했습니다. 각 단계에서 예시 문장과 예외 케이스를 먼저 확인하게 하고, 실제 관광 데이터로 결과를 다시 대조했습니다.

Decisions

실데이터와 실기기에서 막힌 흐름을 고친 과정

Resilience

모듈 하나가 없다고 앱 전체가 죽지 않게

상황

푸시 알림을 붙인 뒤 팀 개발 빌드에서 앱이 시작조차 못 했습니다. Native module NativeRNFBTurboApp is not registered. Firebase·expo-notifications는 import되는 순간 네이티브 모듈을 찾는데, 그 파일이 스토어 → 테마 → 탭 레이아웃으로 이어지는 최상위 의존이라 화면 하나가 아니라 앱이 통째로 뜨지 않았습니다.

판단

재빌드로 덮지 않고 구조로 막았습니다. 실제로 쓸 때만 안에서 require하고, 그 전에 모듈이 있는지부터 확인합니다.

근거

try/catch만으로는 부족했습니다. Metro가 모듈 로드 실패를 먼저 기록해 에러 화면을 띄우기 때문에, 예외를 잡았을 땐 이미 화면이 떠 있습니다. 던지지 않고 확인만 하는 API가 따로 있어 그걸 씁니다.

// expo-modules와 TurboModule은 확인 방법이 다르다
requireOptionalNativeModule('ExpoPushTokenManager') != null &&
TurboModuleRegistry.get('NativeRNFBTurboApp') != null

Trust

보내지 않은 것을 보냈다고 말하지 않기

상황

「사업자에게 확인 요청」을 누르면 "보냈어요"가 떴지만 아무 데도 가지 않았습니다. 로컬 상태만 바뀌는 코드였고, 서버에 그런 엔드포인트가 없었습니다. 「제보하기」도 같은 상태였습니다.

판단

제보는 서버 전송을 붙였고, 붙일 데가 없는 확인 요청은 문구를 사실에 맞게 낮췄습니다. 완료 화면이 1.6초 만에 자동으로 닫히던 것도 확인 버튼으로 바꿨습니다 — 무슨 일이 일어났는지 읽을 시간이 없었습니다.

근거

제보 종류 셋 중 「실제로는 입장됐어요」만 서버에 보내지 않습니다. 거부의 반대인데 거부 제보로 보내면 그 시설을 보려던 다른 사용자에게 없던 경고가 뜹니다. 기능을 붙이는 것보다 데이터를 오염시키지 않는 게 먼저였습니다.

Constraint

인증을 강제하지 않는 인증

상황

여권 도장(방문 기록)에 GPS 현장 확인을 넣기로 했습니다. 시설 반경 안에서 찍었는지 확인하는 기능입니다.

판단

확인하되 막지 않습니다. 반경 밖이거나 위치를 거부해도 도장은 남고, 「현장」 배지만 붙지 않습니다.

근거

반경 밖이거나 위치 권한을 거부해도 기록 기능을 사용할 수 있도록 현장 배지와 분리했습니다. 현장에 없는 심사자도 기능을 확인할 수 있습니다. 반경 1km는 실내 GPS 오차를 고려한 기준이며, 현장 배지가 실제 방문이나 부정 방지를 보장하지는 않습니다.

Build

검증된 것을 지키는 쪽으로

상황

첫 production 빌드가 Install pods 단계에서 실패했습니다. RN 0.75부터 Firebase iOS SDK를 Swift Package Manager로 푸는데, SPM은 use_frameworks! :linkage => :dynamic을 요구합니다.

판단

그 설정을 켜는 대신 Firebase만 CocoaPods로 되돌렸습니다 (disableSPM).

근거

useFrameworks는 Podfile 전체에 걸립니다. 모든 네이티브 모듈의 링크 방식이 바뀌고, 실기기에서 이미 검증을 끝낸 소셜 로그인 4종(카카오·네이버·구글·애플)을 전부 다시 확인해야 합니다. 마감 12일 전에 질 위험이 아니었습니다.

Locale

한글에서만 드러나는 결함

상황

실기기에서 시설 이름의 글자 윗부분이 수평으로 잘려 나왔습니다. 시뮬레이터와 웹에서는 멀쩡했습니다.

판단

lineHeight 누락이었습니다. 한 곳만 고치지 않고 같은 패턴 18곳을 전수 조사해 일괄 지정했습니다.

근거

iOS는 fontWeight: 900 같은 무거운 굵기에서 시스템 폰트 메트릭으로 행 높이를 잡는데, 한글은 폴백 폰트의 ascender가 그보다 커서 넘칩니다. 작은 텍스트에는 lineHeight가 붙어 있는데 큰 제목에만 빠져 있었습니다 — 두 곳만 고쳤으면 다른 화면에서 그대로 다시 나왔을 겁니다.

Data

목 데이터로는 안 드러나는 것

상황

판별을 끝내고 「동반 출입증 보기」를 눌러도 "먼저 AI 판별을 해주세요"가 떴습니다. 핵심 기능 하나가 실서비스에서 통째로 막혀 있었습니다.

판단

출입증 화면이 시설을 목 데이터에서만 찾고 있었습니다. 스토어 캐시를 보도록 바꾸고, 같은 패턴을 홈·제보 화면에서도 찾아 고쳤습니다.

근거

관광공사에서 온 실제 시설은 목 데이터에 없으니 조회가 항상 실패하고, 판별 기록이 있어도 "판별한 적 없음" 분기로 빠졌습니다. 데모용 목 시설로 테스트할 때는 전혀 드러나지 않습니다. 실제 시설 ID로 판별부터 출입증까지 이어지는 경로를 확인해야 찾을 수 있는 결함이었습니다.
