Problem

기존 시스템은 경보에서 멈춥니다

행정안전부 인파관리지원시스템(2025~, 전국 100개소)은 기지국 기반 밀집도를 히트맵으로 보여주고 임계를 넘으면 담당 공무원에게 문자를 보냅니다. 여기까지는 잘 작동합니다.

문제는 그 다음입니다. 문자를 받은 담당자가 "지금 무엇을, 누구에게, 어떤 말로" 지시해야 하는지는 여전히 사람의 몫입니다. 현장 무전과 경찰 공조 요청과 시민 안내방송은 각각 다른 어조와 다른 내용이어야 하는데, 그걸 압박 상황에서 몇 분 안에 만들어야 합니다.

10·29 이태원 참사가 보여준 것처럼 골든타임의 대응 품질이 피해 규모를 결정합니다. CrowdSense는 그 빈 구간 — 감지 다음의 1분 — 을 표준화·자동화합니다. 기존 시스템의 대체가 아니라, 그 경보를 입력으로 받아 대응을 완성하는 보완 레이어입니다.

기존 감지 기지국 밀집도 히트맵

회색은 기존 시스템이 이미 하는 일, 주황은 CrowdSense가 채우는 구간입니다.

Engineering

어려웠던 판단들

기능을 만드는 것보다 "이 수치를 화면에 내보내도 되는가"를 정하는 데 시간이 더 걸렸습니다. 재난 대응 화면에서 틀린 확신은 정보가 없는 것보다 위험합니다.

01

오차가 신호보다 클 때, 모른다고 말하기

서울시는 유입 인원을 정확한 수가 아니라 구간(예: 150~200명)으로 제공합니다. 처음엔 관행대로 중앙값 하나로 눌러서 썼습니다. 그런데 실측해 보니 5분 창 순유입의 구간 폭이 120명(= 24명/분)이었고, 이건 제 초기 구현이 "급증"으로 판정해 빨간 경보를 띄우던 신호와 같은 자릿수였습니다. 오차 안에서 춤추는 값으로 재난 경보를 띄우고 있었던 겁니다.

순유입을 구간 그대로 들고 다니면서, 부호가 결정되는 창(구간이 0을 넘지 않는 창)만 판정에 쓰도록 바꿨습니다. 그런 창이 없으면 판정 불가로 표시합니다. 화면이 비는 게 답답하지만, 모르는 것을 모른다고 말하는 편이 틀린 확신보다 낫습니다.

Measured 5분 창 구간 폭 120명 = 24명/분 · 당시 "급증" 판정 임계 +10명/분
02

같은 +150명/분이 어디서는 무의미하고 어디서는 위험하다

추세를 원 인원(명/분)으로 판정하고 있었습니다. 그런데 체류 인원 8.5만 명인 강남역에서 +150명/분은 아무 의미가 없고, 1.3만 명인 이태원에서는 유의미합니다. 같은 숫자가 지점마다 다른 뜻인데 같은 규칙으로 판정하고 있었던 거죠.

판정 기준을 밀도 변화율로 바꿨습니다. Δ밀도/분 = 현재밀도 × (순유입/분 ÷ 체류인원) — 지역 면적이 일정하다는 전제에서 나오는 식이고, 이 산출 근거를 화면에 함께 노출합니다. 수치만 던지면 관제사가 검증할 수 없습니다.

Measured 강남역 체류 85,000명 vs 이태원 13,000명 — 같은 유입에 6.5배 다른 밀도 영향
03

데이터가 33분 늦게 온다는 사실을 예측식에 반영하기

서울시 공공데이터는 실시간이 아닙니다. 관측 후 노출까지 실측 33분이 걸립니다. 서버 현재 시각을 기준으로 임계 도달 시각을 계산하면, 예측이 통째로 33분 뒤로 밀립니다 — 경보가 구조적으로 늦게 뜹니다.

예측의 기준점을 벽시계가 아니라 관측 시각으로 바꾸고, 화면에는 관측 시각 · 데이터 나이 · 지금 기준 잔여 시간을 함께 표시합니다. 경보 색상도 지금 기준 잔여 시간으로 판정합니다.

Before 서버 현재 시각 기준 → 도달 예상이 33분 뒤로 밀림
→
After 관측 시각 기준 + 데이터 나이 노출 → 경보 시점 정상화
04

AI에게 "하지 마라"고 세 번 말했지만 세 번 다 뚫렸다

분산 목적지로 제시하는 장소 중 절반이 학교 운동장·광장인데, 공공데이터에 개폐 시각 필드가 아예 없습니다. 야간·주말에는 교문이 잠깁니다. 그래서 프롬프트에 "개방 여부를 모르는 곳은 시민 문안에 단독 목적지로 쓰지 마라"를 넣었습니다.

세 라운드에 걸쳐 문구를 강화했고, 세 번 다 뚫렸습니다. 왕십리역 실호출 4회 중 3회가 재난문자에 잠긴 광장을 넣었습니다. 규칙을 "학교 운동장" 중심으로 예시화했더니 모델이 광장에는 적용하지 않더군요.

문구를 더 붙이는 대신 입력에서 갈랐습니다. publicSafeDestinations(시민 문안 허용)와 verifyBeforeUse(조치사항 전용)로 나눠서 넘기니, 같은 케이스 재실행에서 위반이 0건이 됐습니다. 안전 규칙은 모델의 판단에 맡길 게 아니라 입력 구조로 강제해야 한다는 게 이 프로젝트에서 가장 크게 배운 것입니다.

Verified 프롬프트 강화 3회 → 위반 3/4회 · 입력 분리 후 → 위반 0/6회
05

공공데이터가 틀렸을 때 알아채기

분산 가능 공간을 4개 공공데이터셋에서 모으는데, 원본 자체에 결함이 있었습니다.

  • 좌표 오류 — 답십리근린공원은 주소가 동대문구인데 위경도가 강남 위도로 찍혀 있어, COEX 반경 700m 안에 9km 떨어진 공원이 잡혔습니다. 같은 자치구 공원들의 중앙 좌표에서 5km 이상 벗어난 레코드를 버리는 검사를 넣어 걸러냈습니다.
  • 자기모순 — 무더위쉼터 15건이 운영시간은 21시 종료인데 "야간 개방"으로 표기돼 있습니다. 어느 쪽도 단정하지 않고 "확인 필요"로 낮춥니다.
  • 미입력을 폐관으로 접지 않기 — 개폐 필드가 전국 87% 비어 있습니다. 처음엔 이걸 false로 처리했는데, 34.6℃ 폭염 시험에서 모델이 지시를 충실히 따라 쉼터 4곳을 전부 버렸습니다. 폭염 대응이 자기 시나리오에서 무력화된 거죠. "미상"을 별도 상태로 두고 개방 확인을 조치에 넣도록 바꿨습니다.
Result 분산 공간 커버리지 27/32 → 32/32 지점 · 좌표 이상 4건 제외
06

감사 근거가 될 기록이라면 숫자가 맞아야 한다

대응 타임라인과 골든타임 KPI가 브라우저 메모리에만 있어서, 탭을 닫으면 사라졌습니다. 서버 저장을 붙이면서 이벤트 보관 상한(2000건)을 넘으면 앞부분을 자르게 했는데 — 자를 때 첫 경보만 남겼습니다.

그랬더니 잘린 구간에 있던 진짜 첫 조치 대신 살아남은 나중 조치가 "첫 조치"로 계산돼, 골든타임이 30초에서 30,240초로 저장됐습니다. 1008배입니다. 사후 보고에 들어갈 숫자가 틀리면 이 기능은 있으나 마납니다. 기준점 세 개(첫 경보 · 첫 조치 · 첫 전파)를 함께 보존하도록 고쳤습니다.

Bug 골든타임 30초 → 30,240초 (1008배)
→
Fix KPI 기준점 3개 보존 후 30초 / 60초 정확
Reliability

커밋 전 코드 리뷰를 규칙으로 만든 이유

혼자 만드는 프로젝트라 검토해 줄 사람이 없었습니다. 그래서 큰 작업 단위마다 전용 리뷰 에이전트에게 실측 기반 검증을 받고, 보류가 나오면 고쳐서 다시 받는 절차를 규칙으로 박아 뒀습니다.

결과적으로 두 기능에 15라운드가 걸렸습니다. 소모적으로 보이지만, 잡힌 것들이 전부 실제 브라우저에서 끝까지 돌려봐야만 드러나는 종류였습니다. 아래가 제가 놓쳤다가 리뷰에서 잡힌 것들입니다.

R1
치명양자화 오차를 무시한 경보 5분 순유입 오차 폭(24명/분)이 신호(+10명/분)보다 컸습니다. 오차 안에서 빨간 경보가 떴습니다.
R3
치명접근 통제를 우회하는 라우트 API 인증을 붙이면서, 같은 데이터를 주는 다른 경로 하나를 잠그지 않았습니다. 게이트는 하나만 빠져도 전체가 무의미해집니다.
R4
치명조건 안에 넣은 안전 규칙 "없는 장소를 지어내지 마라"를 조건부 블록에 넣었더니, 제약이 가장 필요한 곳에서 무제약이 됐습니다. AI가 지하철역 출구로 인파를 유도했습니다.
R5
치명정렬 규칙이 만든 회귀 "지정 대피장소 우선"으로 정렬했더니 면적을 아는 대형 공원이 밀려났습니다. 인사동에서 탑골공원이 통째로 빠지고 재난문자에 초등학교가 들어갔습니다.
R8
중대축으로 분기해서 생긴 판정 구멍 쉼터 개폐를 "주말이냐 야간이냐"로 분기했더니 평일 낮·주말 심야·새벽이 판정 밖으로 빠졌습니다. 새벽 2시 30분에 잠긴 구청으로 노약자를 보내는 재난문자가 생성됐습니다.
R11
치명"경미" 수정이 기능을 100% 죽임 레벨 화이트리스트에 ALERT_LEVELS를 썼는데, 그건 전체 도메인이 아니라 경보 취급 부분집합이었습니다. 타입 검사도 제 테스트도 통과했고, 실브라우저 검증에서야 드러났습니다.
R14
치명자동 저장이 스스로 한도를 소진 마지막 저장 시각을 응답에서 찍었는데, 새 저장이 이전 요청을 취소하면 그 콜백이 건너뛰어져 값이 영원히 0으로 남았습니다. 디바운스가 무력화돼 재생 1회에 POST 22건이 나갔습니다.
R15
중대깨우는 주체가 없는 백오프 재시도 간격 상수는 있는데 그 시각에 깨우는 타이머가 없어, 실패 후 180초를 방치해도 재시도가 0건이었습니다. 사용자가 보고서를 열어야만 복구됐습니다.

이 과정에서 배운 건 "내가 고친 것이 실제로 동작하는지는 끝까지 돌려봐야만 안다"입니다. R11은 타입 검사·단위 테스트·리뷰를 전부 통과한 변경이 엔드투엔드에서 100% 실패한 사례였고, 그 뒤로는 매 수정마다 헤드리스 브라우저로 실제 저장까지 확인했습니다.

Architecture

서울에서 검증하고 전국으로 넓히는 구조

경진대회 이후 실제 판매 가능한 제품으로 올리면서, 지역·데이터원이 바뀌어도 관제 로직은 그대로여야 한다고 봤습니다. 관제 로직(밀도 분류 · 유입 예측 · 위험도 산정 · AI 지시문)은 공급자 인터페이스의 정규화 타입에만 의존하고, 원본 API 스키마는 각 공급자 구현 안에 갇힙니다.

공급자마다 제공하는 신호가 다르므로 capabilities 배열로 선언하고, 화면은 없는 신호를 숨기지 않고 "이 지역은 이 데이터가 없음"으로 표시합니다. 커버리지 공백을 감추면 관제사가 "데이터에 없음"과 "실제로 없음"을 구분할 수 없습니다.

접근 통제도 판매를 전제로 설계했습니다. API 키는 해시로만 환경변수에 보관하고 (평문은 발급 시점에만 존재), 조회용 키와 운영용 키를 분리했으며, 데모 경로는 브라우저가 직접 붙여 위조할 수 없는 Sec-Fetch-Site 헤더로 출처를 가릅니다.

이 프로젝트로 말할 수 있는 것

자기소개서·면접에서 그대로 꺼내 쓸 수 있는 형태로 정리했습니다.

데이터를 의심하는 태도

공공데이터를 그대로 믿지 않고 오차 구조부터 확인했습니다. 유입 인원이 구간으로 제공된다는 사실을 확인하고 실측해 보니, 오차 폭이 제가 경보 기준으로 쓰던 신호와 같은 자릿수였습니다. 중앙값으로 눌러 쓰던 구현을 구간 그대로 다루도록 바꾸고, 부호가 결정되지 않는 구간에서는 "판정 불가"를 표시하도록 했습니다. 화면을 채우는 것보다 틀린 확신을 내보내지 않는 것이 중요하다고 판단했습니다.

AI를 신뢰 경계 안에서 쓰는 법

LLM에 안전 규칙을 프롬프트로 세 라운드에 걸쳐 강화했지만 세 번 다 위반이 재현됐습니다. 문구를 더하는 대신 입력 자체를 두 목록으로 분리해 시민 문안에 쓸 수 있는 장소와 확인이 필요한 장소를 구조적으로 갈랐고, 재실행에서 위반이 0건이 됐습니다. 모델의 판단에 맡길 것과 코드로 강제할 것을 구분하는 기준을 이 과정에서 얻었습니다.

검증 없이는 고쳤다고 말하지 않기

커밋 전 코드 리뷰를 규칙으로 두고 두 기능에 15라운드를 수행했습니다. 타입 검사와 단위 테스트를 모두 통과한 수정이 실제 환경에서는 기능을 완전히 중단시킨 사례를 겪은 뒤로, 모든 수정을 헤드리스 브라우저로 끝까지 실행해 서버에 데이터가 남는지까지 확인하는 절차를 만들었습니다. "동작한다"를 주장이 아니라 측정으로 말하는 습관이 생겼습니다.

도메인을 이해하고 만드는 것

인파 관제에서는 "어디로 빼낼 것인가"가 핵심인데, 지하 공간·지하철역 출구·좁은 계단은 절대 목적지가 될 수 없습니다. 가이드라인을 읽고 이 제약을 시스템에 못 박았고, 어린이공원처럼 이름만 공원인 곳, 야간에 문이 잠기는 학교 운동장, 궁궐처럼 폐장 시각이 있는 시설을 각각 다른 규칙으로 걸러냈습니다. 기술적으로 맞는 답과 현장에서 실행 가능한 답이 다르다는 걸 배웠습니다.
